# Ontology build study

This experimental ref measures native PostgreSQL ontology maintenance. The running public seed builders use their original image, checkpoints and provider capacity. The study workflow executes only on its own ref and uses the repository's synthetic HTTP provider and disposable PostgreSQL 18 containers. The matched-hour investigation records source and receipt identities, timing, queue writes, reported tokens and the witnessed freshness rejection. [Discovery evidence](https://github.com/markhuangai/dense-mem/issues/657#issuecomment-7084374063)

## Paired synthetic measurements

The source/organized/definition-marker counts and the ratio of batch appearances to distinct Evidence come from the frozen November 22 samples. The generator scales eligible sources, organized sources and outstanding definition markers by 64, sets overlapping change vocabulary from the appearance ratio, and includes disjoint topic changes. Background topic count is a synthetic catalog-size parameter. The result applies to the measured workload shapes. It does not directly estimate a dataset's remaining build time.

A PostgreSQL template contains real canonical Evidence, prior organizations, durable receipts and pending marker cursors. The two arms clone that same template. Fixed-schedule probes compare full ordered topic records and the actual structured provider request after replacing the generated request ID. A controlled manager publication after the first committed discovery page introduces a new topic and corrects one source. Eight slots are available in the native scheduler. The timing includes discovering, organizing, publishing, consuming all markers and verifying a paused, drained state. Each arm records provider usage, correction latency, per-page timing and counts, oldest marker age, committed requeues and the final normalized semantic and Recall results.

The four alternating base/candidate pairs for each dataset run on the same GitHub-hosted runner. The workflow selects the study variant. The topic-filter trial changes one predicate in the actual GORM Rows execution path. The quality job compiles the selected query separately and exercises it with the real organization, matching, publication, row-level security and Recall cohorts.

The primary comparison uses HotpotQA and MuSiQue. A trial advances to the remaining shapes if every timed pair finishes faster, the median paired saving exceeds baseline median absolute deviation, the correction measurements do not show a repeatable regression, and all correctness checks pass. This screening rule is an experiment decision. Preserve every individual result. A failed or incomplete pair leaves the comparison inconclusive.

## Pending Evidence refresh

The pending-refresh workflow compares four arms in the order `ABDC`, `BCAD`, `CDBA`, `DACB`. A and B use the original vocabulary lookup. C and D install the same stored vectors. B and D also read the live batch closures once per nonempty definition page and skip a forced rewrite of an identical, eligible pending row outside those claims. The PostgreSQL conflict predicate still locks the row. A reported skip represents an avoided update and revision bump.

The hosted report checks effective discovery pages of 100, the SQL used by each arm, and the fixed-schedule requests and candidates. It keeps committed pending skips, ordinary no-ops, new pending rows, pending rewrites and requeues as separate counters. A timed arm needs a committed skip to earn credit. Both comparisons share the same correction, provider usage and completion measurements. Compare B with A and D with C. If either comparison passes HotpotQA and MuSiQue, all four arms run against the remaining three shapes. A change to the original queue requires B to qualify on all five shapes. D measures the effect with the stored-vector dependency. [Previous experiment](https://github.com/markhuangai/dense-mem/issues/657#issuecomment-7088049520)

## Rank topic IDs before loading revisions

Each hosted dataset job runs the original lookup, stored vectors, and rank-first hydration in four blocks. The execution orders are original/vector/rank-first, rank-first/vector/original, vector/rank-first/original, and original/rank-first/vector. The job records the SHA-256 of the frozen PostgreSQL template dump and correction fixture. Each arm uses a fresh clone. Both vector arms pay for the same projection installation, backfill, index, initial verification, and transactional publication. The clock stops after verified full coverage, pause, and drain. The correction latency includes publication, matching the earlier trials. The receipt also gives latency from commit to Recall visibility.

Use the per-dataset artifacts for raw query plans, actual page sizes, fixed-schedule HTTP request bodies, completed timings, and the stage reached on failure. The actual SQL fingerprints must match the separately compiled PostgreSQL cohorts. Query plans use identical bindings on untimed clones. A materialized page must precede payload hydration. Rows, loops, buffers, and indexes show whether PostgreSQL restricted its payload work to that page. The measured query plan determines GIN use.

The HotpotQA target is a median of at least 13% saved against the original over the four matched blocks. Both primaries must pass the existing original-relative screen before the other three shapes run. A production recommendation for rank-first also requires repeatable savings over stored vectors on both primaries, using the same screen. A missing repetition or correctness receipt makes the comparison inconclusive.

The vector trial renders the existing PostgreSQL expression and pinned stop words from the tested source. It stores the vector by team, shared space, generation, topic and revision. A PostgreSQL trigger inserts each new value in the publication transaction. A GIN index supports lexical matching. Forced row-level security uses the topic payload's read and insert policies. The control runs the original lookup. The candidate measures installation, backfill, index construction, verification and publication. It records an actual query plan, including the indexes visited, and reconciles every current topic vector against the live expression before and after maintenance. The quality job installs the study migration only in its disposable checkout and databases. Activating such a projection in a deployed database would require a separately reviewed, bounded backfill and a verified read switch.

The page-size trial compares 25 with the native 100 inside the existing team lease. After initial enumeration, an ordinary turn selects 25 if at least 50 eligible pending sources lie outside all active batch claims in the same shared space and generation. This experimental threshold keeps two short pages of ordinary work available. Initial enumeration, manual retries and the final drain retain the caller's page size. The elapsed time includes the queue inspection. Each arm records the effective limits, time to the first batch, and the summed duration and p95 of discovery pages immediately preceding a successful batch claim on the same lease. Use the same template, correction, accuracy and completion checks for each trial.

Two further template clones each run three serial native maintenance turns, with the same topic publication and manager correction between turns one and two. Each turn retains its effective page size, selected Evidence, full ordered candidate records seen by the organizer, and structured inputs decoded by the HTTP provider fixture. The comparison lists every turn where sources, ordered candidates or requests differed. Only the generated request ID is excluded from that comparison. Changed inputs require fresh paired answers at the public accuracy gate.

## Public accuracy comparison

Fresh provider-backed comparisons begin after all five original builders finish. Before changing production code, record the maintainer's issue-specific approval of the public QA replacement for the retired deterministic 1k runner. Issue 809 records the earlier, separately scoped replacement. [Earlier approval](https://github.com/markhuangai/dense-mem/issues/809)

1. Verify each parent by digest. Prepare two independent ontology-on children from that parent using the baseline and candidate source/image, eight workers, the same maintenance policy and the `dense-mem-testing` model with a 500,000-token window. Retain both immutable child digests and the signed-off source/image identities, full positive native coverage, canonical hash, terminal usage, and paused/drained receipts. Use the supported seed builder and hosted scoring entry points. [Seed and scoring guide](https://github.com/markhuangai/dense-mem/blob/214fee2f8d3ac53333857888dcdd2ce56a367fa9/tests/eval/README.md)
2. Score a shared off control and each independent child on the same questions, model, settings and both answer policies. Use fresh answers when inputs change. Any replay must prove byte equality of complete protected model requests including messages, schema, decoding settings and model identity.
3. Download verified numeric score artifacts. Run the following comparison for each independent repetition. It rejects a shared child, mismatched parent, missing question, incomplete capture or a partial build. Inspect per-question changes in retrieval, supporting-text coverage, citation counts, exact match and F1 separately for each dataset/policy.

```bash
python3 tests/eval/scripts/ontology_build_quality.py \
  --off "$off_reports" --base-on "$base_reports" --candidate-on "$candidate_reports" \
  --base-sha "$base_source" --candidate-sha "$candidate_source" --output "$numeric_comparison"
```

When model inputs or outcomes differ, repeat the matched comparison with baseline-versus-baseline controls on the same questions. Preserve per-question paired deltas and sampling uncertainty. Hold any accuracy regression or unresolved effect. A numeric tie by itself cannot prove identical topic rankings or model inputs. Choose a production change only after a repeatable full-drain improvement and the applicable accuracy evidence.
