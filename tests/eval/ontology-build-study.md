# Ontology build study

This experimental ref measures native PostgreSQL ontology maintenance. The running public seed builders use their original image, checkpoints and provider capacity. The study workflow executes only on its own ref and uses the repository's synthetic HTTP provider and disposable PostgreSQL 18 containers. The matched-hour investigation records source and receipt identities, timing, queue writes, reported tokens and the witnessed freshness rejection. [Discovery evidence](https://github.com/markhuangai/dense-mem/issues/657#issuecomment-7084374063)

## Paired synthetic measurements

The source/organized/definition-marker counts and the ratio of batch appearances to distinct Evidence come from the frozen November 22 samples. The generator scales eligible sources, organized sources and outstanding definition markers by 64, sets overlapping change vocabulary from the appearance ratio, and includes disjoint topic changes. Background topic count is a synthetic catalog-size parameter. The result applies to the measured workload shapes. It does not directly estimate a dataset's remaining build time.

A PostgreSQL template contains real canonical Evidence, prior organizations, durable receipts and pending marker cursors. The two arms clone that same template. Fixed-schedule probes compare full ordered topic records and the actual structured provider request after replacing the generated request ID. A controlled manager publication after the first committed discovery page introduces a new topic and corrects one source. Eight slots are available in the native scheduler. The timing includes discovering, organizing, publishing, consuming all markers and verifying a paused, drained state. Each arm records provider usage, correction latency, per-page timing and counts, oldest marker age, committed requeues and the final normalized semantic and Recall results.

The four alternating base/candidate pairs for each dataset run on the same GitHub-hosted runner. The first trial changes one predicate in the actual GORM Rows execution path. The quality job compiles the same one-line SQL change separately and exercises it with the real organization, matching, publication, row-level security and Recall cohorts. The process never reads a builder's runtime database.

The primary comparison uses HotpotQA and MuSiQue. A trial advances to the remaining shapes if every timed pair finishes faster, the median paired saving exceeds baseline median absolute deviation, the correction measurements do not show a repeatable regression, and all correctness checks pass. This screening rule is an experiment decision. Preserve every individual result. A failed or incomplete pair leaves the comparison inconclusive.

If the measured vocabulary work still dominates, the next isolated trial precomputes the existing PostgreSQL text vector once per scoped topic revision and measures publication and backfill as well as lookup. Preserve the names, description, pinned stop words, positions, forced candidates, pagination and live checks. If discovery still delays batches while ordinary work is queued, compare a 25-source page with 100 after initial enumeration. Drain the remaining markers with full pages. Use the same template, correction, accuracy and completion checks for each trial.

## Public accuracy comparison

Fresh provider-backed comparisons begin after all five original builders finish. Before changing production code, record the maintainer's issue-specific approval of the public QA replacement for the retired deterministic 1k runner. Issue 809 records the earlier, separately scoped replacement. [Earlier approval](https://github.com/markhuangai/dense-mem/issues/809)

1. Verify each parent by digest. Prepare two independent ontology-on children from that parent using the baseline and candidate source/image, eight workers, the same maintenance policy and the `dense-mem-testing` model with a 500,000-token window. Retain both immutable child digests and the signed-off source/image identities, full positive native coverage, canonical hash, terminal usage, and paused/drained receipts. Use the supported seed builder and hosted scoring entry points. [Seed and scoring guide](https://github.com/markhuangai/dense-mem/blob/214fee2f8d3ac53333857888dcdd2ce56a367fa9/tests/eval/README.md)
2. Score a shared off control and each independent child on the same questions, model, settings and both answer policies. Use fresh answers when inputs change. Any replay must prove byte equality of complete protected model requests including messages, schema, decoding settings and model identity.
3. Download verified numeric score artifacts. Run the following comparison for each independent repetition. It rejects a shared child, mismatched parent, missing question, incomplete capture or a partial build. Inspect per-question changes in retrieval, supporting-text coverage, citation counts, exact match and F1 separately for each dataset/policy.

```bash
python3 tests/eval/scripts/ontology_build_quality.py \
  --off "$off_reports" --base-on "$base_reports" --candidate-on "$candidate_reports" \
  --base-sha "$base_source" --candidate-sha "$candidate_source" --output "$numeric_comparison"
```

When model inputs or outcomes differ, repeat the matched comparison with baseline-versus-baseline controls on the same questions. Preserve per-question paired deltas and sampling uncertainty. Hold any accuracy regression or unresolved effect. A numeric tie by itself cannot prove identical topic rankings or model inputs. Choose a production change only after a repeatable full-drain improvement and the applicable accuracy evidence.
